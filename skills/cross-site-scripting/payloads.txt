# XSS payload corpus for skills/cross-site-scripting/SKILL.md — two
# sections, matching the two payload-bearing stages of the actual
# workflow. This deliberately does NOT mirror sql-injection/payloads.txt's
# phase count: the two vulnerability classes have different workflows, and
# forcing XSS into the same number of phases would create sections with no
# real gate behind them. See SKILL.md "Workflow at a glance" and
# "Relationship to payloads.txt".
#
#   - Phase 1 (below): a plain-text DETECTION MARKER. Not executable. Used
#     only to observe where and how the input lands in the response
#     (encoded, inside a tag, inside an attribute, inside a script, etc.)
#     before any execution is attempted.
#
#   - Phase 2 (below): CONTEXT-SPECIFIC EXECUTION MARKERS. These do execute
#     JavaScript — call them what they are. The safety property they carry
#     is that the *action* performed is harmless and self-contained
#     (setting document.title to a known value), not that they avoid
#     running code. Use only the entry matching the context you actually
#     observed in Phase 1 — do not try every context's entry against one
#     candidate.
#
# There is no Phase 3 or Phase 4 in this file. Stored XSS and DOM-based
# XSS are not separate payload categories — they reuse whichever Phase 2
# entry matches the observed context; what differs is workflow (where the
# payload is submitted, when/to whom it renders back), which SKILL.md
# handles, not this corpus. Do not add a new phase section here without a
# corresponding ask_user-gated phase being defined in SKILL.md first.
#
# No browser-execution capability is available in the current runtime.
# Phase 2 markers establish an execution *hypothesis* from HTTP-level or
# source/sink evidence. When that evidence is not deterministic (e.g. a
# JS-string break-out, or a DOM sink whose actual execution can't be
# observed), SKILL.md requires recording `browser-required`
# and stopping — do not attempt to simulate or infer browser execution
# using shell, http, or any other substitute for an actual browser.
#
# None of these payloads exfiltrate cookies, tokens, or page content, and
# none chain into session hijacking, credential capture, keylogging, or
# redirection to an external site. They are absent from this default corpus;
# any separate controlled-impact path needs its own approval gate and
# supported runtime capability, as described in SKILL.md.

# ============================================================================
# ===================== PHASE 1 — CONTEXT DETECTION ==========================
# ============================================================================
# Plain text only. No HTML/JS metacharacters that would themselves prove
# anything — the point is to see how the *marker itself* is transformed
# (stripped or passed through) to establish input propagation. Use the
# metacharacter probe to assess encoding before an execution attempt, then
# select only the observed context's Phase 2 entry.

xsspoc{TIMESTAMP}                     # purpose: baseline marker with no special characters | applies: every candidate, always run first | limit: establishes propagation only, not encoding or execution
xsspoc{TIMESTAMP}"'<>                 # purpose: marker followed by the four characters most output-encoding schemes transform (", ', <, >) | applies: every candidate, second detection request | limit: observe which characters survive unescaped; still not an execution attempt

# Replace {TIMESTAMP} with a fresh value per candidate (e.g. unix epoch
# seconds) so repeated runs against the same parameter don't collide with
# stale reflected/stored values from a previous test.
#
# Read the response around the marker and classify the context per
# SKILL.md step 2 (html-body | html-attribute | js-string | url |
# html-comment | fully-encoded) before moving to Phase 2. For URL/href/src
# contexts, inspect the HTML-decoded attribute value, scheme validation and
# canonicalization per SKILL.md step 2. HTML encoding alone does not establish
# safety in a URL or event handler; unknown handling is not a tested negative.

# ============================================================================
# ============== PHASE 2 — CONTEXT-SPECIFIC CONFIRMATION =====================
# ============================================================================
# One execution marker per observed context. Use only the entry matching
# what Phase 1 showed. Each sets document.title to a value containing the
# candidate's marker — visible proof of execution that reads nothing
# sensitive and sends nothing off-session. Replace {MARKER} with the same
# value used in Phase 1 for that candidate so the result is traceable.
# text/html fragments need no html/body wrappers. Raw reflection alone is
# not complete executable proof. If evidence shows deterministic removal of
# one trailing character, SKILL.md permits one same-context close variant:
# append one inert trailing character to the selected marker, then inspect
# the returned complete syntax. This replaces any other close variant; no
# additional phase, spray, encoding trick or browser simulation is allowed.
# Failed variants support not-confirmed only after a completed bounded test with
# usable proof; missing browser execution stays browser-required, and missing
# required captures/proof stays insufficient-evidence (SKILL.md step 5).

# --- HTML body context --------------------------------------------------
<script>document.title='xsspoc-{MARKER}'</script>
    # purpose: direct script execution in an unescaped HTML body position
    # applies: marker in Phase 1 rendered between tags, unescaped
    # limit: execution marker only — do not substitute a payload that reads document.cookie or similar

<img src=x onerror="document.title='xsspoc-{MARKER}'">
    # purpose: event-handler-based close variant for HTML body context
    # applies: ONLY if the <script> entry above specifically failed to execute while Phase 1 showed the marker otherwise landing unescaped — i.e. testing whether the app's sanitizer covers event-handler attributes as well as <script> tags, not evading a WAF or security control
    # limit: this is the one close variant allowed by SKILL.md step 3 for this context — if this also fails, stop under SKILL.md step 5 rather than trying further tag/attribute combinations

# --- HTML attribute context ---------------------------------------------
"><script>document.title='xsspoc-{MARKER}'</script>
    # purpose: break out of a quoted attribute value, then execute
    # applies: marker in Phase 1 rendered inside a double-quoted attribute, unescaped
    # limit: match the observed attribute quote first; do not test both quote styles when it is known; apply SKILL.md step 5 if unresolved

'><script>document.title='xsspoc-{MARKER}'</script>
    # purpose: single-quote variant of the attribute breakout above
    # applies: same as above, for single-quoted attribute values
    # limit: use first for a known single-quoted attribute; if tried after a failed probe, it consumes SKILL.md step 3's one close-variant allowance

# --- JavaScript string context -------------------------------------------
';document.title='xsspoc-{MARKER}';//
    # purpose: break out of a single-quoted JS string literal, then execute
    # applies: marker in Phase 1 rendered inside a JS string (e.g. var x = 'MARKER';)
    # limit: HTTP-level evidence of this succeeding is usually not deterministic — per SKILL.md step 3, record browser-required unless the response makes the break-out and execution position unambiguous

";document.title='xsspoc-{MARKER}';//
    # purpose: double-quote variant of the above
    # applies: same as above, for double-quoted JS string literals
    # limit: same browser-required caveat as above

# --- URL / href / src context ---------------------------------------------
# Select this only when captured context supports a potentially executable scheme
# after HTML attribute decoding, scheme validation and canonicalization. An
# encoded attribute is not automatically safe; a verified safe-scheme restriction
# can neutralize this vector. Unknown handling remains unresolved; do not spray.
javascript:document.title='xsspoc-{MARKER}'
    # purpose: scheme-based execution when the value is placed directly into an href/src with no scheme validation
    # applies: only for the evidenced scheme-capable element/context described above
    # limit: execution here typically requires a user action (click/navigation) to trigger — note this in evidence/notes; do not simulate a click via automation this skill doesn't have

# --- HTML comment context ---------------------------------------------------
--><script>document.title='xsspoc-{MARKER}'</script><!--
    # purpose: close the surrounding HTML comment, execute, then reopen a comment to keep the rest of the page well-formed
    # applies: marker in Phase 1 rendered inside an HTML comment, unescaped
    # limit: execution marker only, same as the HTML body entry

# --- CSS context: style attribute (e.g. <div style="color: MARKER">) -------
red;"><script>document.title='xsspoc-{MARKER}'</script><div style="
    # purpose: close the style attribute's quote and the tag itself, then execute, then reopen a dummy attribute so the rest of the page stays well-formed
    # applies: marker in Phase 1 rendered inside a style="..." attribute value, unescaped
    # limit: mechanically the same breakout as HTML attribute context, not the <style>-block entry below — do not use this against a marker that landed inside a <style> block instead
    # note: modern browsers do not support CSS expression()-style execution; this is an HTML breakout, not CSS execution. Spend at most this one probe, then apply SKILL.md step 5.

# --- CSS context: <style> block (e.g. <style>body{color:MARKER}</style>) ---
color:red;}</style><script>document.title='xsspoc-{MARKER}'</script><style>{
    # purpose: close the surrounding <style> block and execute, then reopen a dummy style block so the rest of the page stays well-formed
    # applies: marker in Phase 1 rendered inside a <style>...</style> block, unescaped
    # limit: mechanically the same breakout as HTML comment context (close/reopen the enclosing construct), not the style-attribute entry above — do not use this against a marker that landed inside a style="..." attribute instead
    # note: same legacy-browser caveat as above — spend at most this one probe, then apply SKILL.md step 5

# analysis without observed execution supports browser-required, not confirmed.
# A live payload is unnecessary when missing browser proof cannot be resolved.
# Ordinary innerHTML script insertion is not execution. If a live probe is useful, use

# HTML) — there is no separate DOM-specific payload set.
