## 1. Executive summary

Run 02 scheduled and completed all 40 workers. The evaluator reports 21 evaluable cases (8 TP, 11 TN, 0 FP, 2 FN) and 19 unresolved (18 missing canonical result, 1 insufficient evidence). Its 100% precision and 80% recall are arithmetically consistent over the evaluable set. They do not describe all 40 cases: only 52.5% of the run was evaluable, including 4/20 SQLi cases and 17/20 XSS cases. “Worker completed” records process completion, not successful validation.

This audit confirms an important difference between evaluator labels and evidence quality. The positive SQLi case `BenchmarkTest00441` has parser-sensitivity evidence, but does not meet the SQL-injection skill’s stated SQLI-2 confirmation rule. Conversely, `BenchmarkTest02597` is an evaluator false negative even though a permitted close-variant response contains a complete, unescaped script in `text/html`. `BenchmarkTest02186` is the clearest positive SQLi example. The HTTP evidence for most XSS positives is well bound and sufficient under the skill’s ordinary HTML-body rule; browser execution was not recorded and should not be claimed.

Eight finding artifacts are present, matching the eight evaluator TP labels. Their existence does not independently validate proof semantics: `00441` needs qualification, while `02186` is the strongest SQLi proof.

The main operational issue is workflow closure. All 18 missing-result cases reached candidate validation and created an active attempt; 17 dispatched HTTP, but none wrote a canonical `ValidationResult`. Their raw worker results record nine `all_tools_refused` stops and nine `workflow_stalled` stops; there are no `max_steps` stops. Nine traces contain an explicit denial for `read_http_observation` (eight ended `all_tools_refused`; `01389` ended `workflow_stalled`), while `02282` ended `all_tools_refused` after headless `ask_user` could not receive an answer. Other traces show evidence-reference or designated-input errors. The published event stream omits `stop_reason`, but each internal worker result preserves it. The one additional unresolved case (`02357`) recorded `insufficient-evidence` because the designated input was guarded and no baseline reference was available.

**Trust assessment:** useful as a progress and systems-behavior run; not ready as a final benchmark claim. Keep the evaluator’s published numbers unchanged, but qualify them as results on the evaluable subset and separately report unresolved coverage. Before a thesis result, resolve canonical-result closure and independently review semantic evidence, then rerun the affected cases and a complete 40-case evaluation under a recorded, reproducible runtime.

## 2. Method and source of truth

The audit inspected the Run 02 and Run 01 manifests, per-case report CSVs, evaluator partitions and report JSON, event log, raw internal `CaseExecution` JSON, per-case result projections, findings, session/workflow state, transcripts, HTTP observations, and evidence references. Each case was joined by benchmark case ID to the evaluator’s ground-truth and outcome records. Ground truth was read only during this audit; the run harness supplies operational case input to the Agent separately (`benchmarks/scenario1/core/runtime.py`, especially `prompt()` and `execute_case()`). No ground truth or result was written back to the run.

Evaluator outcome is reported as published. Evidence quality is an independent manual assessment against the request/response artifacts and the relevant playbooks (`skills/sql-injection/SKILL.md`; `skills/cross-site-scripting/SKILL.md`). The evaluator validates structural identity and bindings through `benchmarks/scenario1/core/canonical.py`, then compares the accepted Agent outcome with ground truth in `benchmarks/scenario1/core/evaluate.py`; it does not independently decide whether a parser error establishes SQLI-2 or whether a reflected script is executable in the recorded context.

The raw worker result `results/<case-id>.json` records the Agent `stop_reason`; the published event stream and CSV projection omit it. The table uses the raw value. Run 02 records 19 `final_response`, 9 `all_tools_refused`, 10 `workflow_stalled`, and 2 `workflow_blocked` stops. The 10 stalled cases include nine missing canonical results and `01660`, which has a confirmed result but unresolved cleanup state. These are runtime stop labels; the trace evidence below explains the known underlying blockers separately.

Table notation: `GT 1/0` means evaluator-only positive/negative ground truth; endpoint paths are relative to the target base `/benchmark`; `tools P/E` means tool proposals / executed tools; `HTTP D/A` means dispatches / admitted requests; `evidence S/A` means canonical selected evidence references / admitted HTTP requests. `R` is the Agent’s structured result, `—` is no canonical result, and `I-E` is the recorded insufficient-evidence result. Every worker status was `completed`. `B*` means built-in intelligence retrieval is possible from a deterministic source-level reconstruction, not captured prompt telemetry; see section 5. Evidence `N/O` means no canonical evidence references were submitted, so a semantic evidence verdict cannot be made from the result record.

For terminal results, `bound` means the evaluator accepted the run/execution and candidate identity plus the evidence source’s case, method, route, input name, location, and component binding; frozen assessment provenance also matched its attempt/epoch. This is a structural binding check, not a semantic evidence verdict.

### 4.2 One insufficient-evidence result

`BenchmarkTest02357` is SQLi-positive ground truth but was explicitly recorded as `insufficient-evidence`. The designated input component is `name`, with supplied value `bar`, in a POST body to `/sqli-05`. The trace reports that the designated input is immutable under the supplied-input guard and candidate replay is unavailable without a `baseline_request_ref`; the two admitted HTTP requests did not produce selected proof references. The Agent did not establish a SQLi signal, so this should remain unresolved rather than being forced into a negative or positive label. The immediate evidence gap is a captured baseline request tied to the designated component, plus a replay that changes only that component.

### 4.3 Why SQLi evaluability is 20% while XSS is 85%

SQLi produced 4 canonical evaluable results out of 20, with 15 missing results and one insufficient result. XSS produced 17 out of 20, with three missing results. Most SQLi validations proceed into multi-step candidate/attempt management, payload selection, repeated HTTP comparisons, and evidence-parent bookkeeping. Several then fail to commit a terminal result even after admitted probes. The observed reader permission and reference failures are concentrated in SQLi, while the SQLi validation contract requires stronger comparison structure than a single reflection check. By contrast, most XSS cases can conclude from a small number of properly bound responses showing either a complete unescaped script or encoding/no reflection. This explains the difference as **workflow/evidence closure and proof-contract friction**, not as a demonstrated network outage or a higher SQLi attack difficulty. Among unresolved SQLi cases, eight stop as `workflow_stalled`, seven as `all_tools_refused`, and one (`02357`) as `workflow_blocked` with an explicit insufficient-evidence result. The specific underlying cause is confirmed for several trace groups and remains unidentified for `00200`, `01818`, `02176`, and `02546`.

## 5. Intelligence impact audit

The benchmark harness creates a fresh workspace root for each case and constructs `MemoryStore` and `IntelligenceStore` against that root (`benchmarks/scenario1/core/runtime.py::build_agent`). `src/paths.py` then resolves project data below that case workspace’s `.kagent`; the harness supplies a case-local personal home under `.personal`, rather than the operator’s global `~/.kagent`. The 40 cases have separate workspaces and sessions. Therefore, the project-level `.kagent/intelligence/scenarios.jsonl` opened in the IDE and `/home/khainguyen/.kagent/intelligence/scenarios.jsonl` are not the stores injected into these benchmark agents. A case cannot inherit another case’s dynamically learned project or personal intelligence through this setup.

Run 02 contains a per-case project intelligence file in 12 of the 40 workspaces, with one generated lesson associated with that case; the other 28 have no such file. These entries are generated during/after their own session and are not evidence of cross-case retrieval. No case-local personal intelligence file was observed. The run artifacts do not log the exact intelligence context included in each model request.

Source review shows `src/agent/agent.py::build_intelligence_context()` searches the current prompt, target, and session memory, applies a score threshold, and formats up to five results as explicitly untrusted historical context. ## 6. Evidence validity and vulnerability-specific conclusions

### 6.1 SQL injection

The SQL injection skill distinguishes syntax sensitivity (SQLI-1) from confirmed SQLI-2. Its guidance explicitly says repeated malformed syntax errors and parser messages alone do not establish SQLI-2; a Boolean method needs a repeatable true/false differential, and error-based proof must show controlled SQL evaluation (`skills/sql-injection/SKILL.md`, sections “Bound the proof,” “Record a validation result,” and error-based examples).

| Case | Evaluator | Independent evidence review |
|---|---|---|
| `BenchmarkTest02186` | TP | **SUPPORTED.** POST body input to `/sqli-04`. Two repeated true/false pairs share a request template. True predicates return a row (`3, foo, bar`); false predicates return an empty result. Four referenced observations bind to the candidate and attempt. This is the strongest thesis SQLi example. |
| `BenchmarkTest00441` | TP | **PARTIALLY SUPPORTED.** POST body input to `/sqli-00`. Baseline/quote/structural probes produce a SQL parser error (`SQLSyntaxErrorException`, row/column mismatch); Boolean sides both produce the same 500 parser error. This supports syntax sensitivity, not the claimed controlled SQLI-2 evaluation. The finding labels error-based SQLI-2 despite its own note that Boolean confirmation failed. The severity `high` and cleanup status `requires-user-action` are not supported by demonstrated data extraction or a verified cleanup result. The trace includes a successful write acknowledgement, so do not describe the run as purely read-only impact. |
| `BenchmarkTest01215` | TN | **SUPPORTED for the tested header input.** Selected responses show the baseline and Boolean probes returning the same query response. This is a bounded negative for the declared parameter and attempted technique, not exhaustive SQLi absence. |
| `BenchmarkTest01811` | TN | **PARTIALLY SUPPORTED.** Thirteen requests were admitted and the selected observations are identical, but only 2/13 are referenced in the result. Preserve this as a limited negative; the number of probes is comparatively high for evidence that was not retained. |

The other 16 SQLi cases are unresolved, not negatives. `02357` accurately records insufficient evidence. The two SQLi TP labels should not be presented as equal-quality validation: `02186` is supported; `00441` needs qualification and independent re-review before use as a confirmed SQLI-2 result.

### 6.2 Cross-site scripting

The XSS playbook says reflection alone is not confirmation. It permits HTTP-only confirmation when an unescaped, complete executable construct appears in a deterministic ordinary HTML context; it requires `browser-required` when execution depends on browser behavior. No browser execution is present in this benchmark, but that absence does not invalidate a complete script in a normal `text/html` body under the playbook’s rule (`skills/cross-site-scripting/SKILL.md`, reflection-context and confirmation sections).

| Case(s) | Evaluator | Independent evidence review |
|---|---|---|
| `BenchmarkTest00390`, `00725`, `01257`, `01660`, `02131` | TP | **SUPPORTED.** Each has candidate-bound HTTP evidence with a complete unescaped script in a deterministic HTML response. No browser execution should be claimed. `01660` also has an inconsistent mutation/cleanup flag: the trace is a stateless GET/reflection, yet the record says `mutation_performed=true` and leaves cleanup pending. |
| `BenchmarkTest01923` | TP | **PARTIALLY SUPPORTED.** A complete script appears in the HTML response from a `Referer` header input. The response supports injection in that server-side context; the trace does not establish a practical victim delivery path or browser execution for the header value. |
| `BenchmarkTest02597` | FN | **SUPPORTED positive evidence; Agent label contradicted.** GET query input to `/xss-05`. The input filter alters the last character; one allowed close variant yields a complete `<script>…</script>` followed by `Z` in the full `text/html` body. The Agent’s claim that the closing `>` is missing conflicts with the selected complete response. This is the clearest evaluator false negative. |
| `BenchmarkTest01919` | FN | **PARTIALLY SUPPORTED.** A complete unescaped script is reflected from the `Referer` header in HTML, while the Agent returns not-confirmed because victim browser delivery through `Referer` was not shown. Evaluator ground truth expects positive; the observed injection context is real, but practical reachability remains an explicit limitation. |
| `BenchmarkTest01663`, `02694`, `00722`, `00712`, `02692`, `01924` | TN | **SUPPORTED for tested inputs.** Captured evidence shows no reflection or encoding of tested metacharacters across the selected responses. |
| `BenchmarkTest01777`, `01659`, `01048` | TN | **PARTIALLY SUPPORTED.** One response per case; it shows no marker or encoded input, but gives less repeated evidence than the other negative cases. |
| `BenchmarkTest02490`, `01418`, `02129` | unresolved | **INSUFFICIENT / NOT OBSERVABLE.** No canonical result. `02490` and `02129` are blocked at the reader permission; `01418` never gets an admitted probe because of the designated-component guard. |
